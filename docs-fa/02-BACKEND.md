# 🖥️ راهنمای کامل بک‌اند روتینو

> **بک‌اند یعنی چی؟** سروری که جدا از اپ اجرا می‌شه و کارهایی رو انجام می‌ده که نباید دست کاربر باشه: ورود با پیامک، حساب‌وکتاب اشتراک، پرداخت با درگاه، و پنل مدیریت.
> همه‌ی بک‌اند داخل پوشه‌ی **`backend/`** است و کاملاً مستقل از فرانت اجرا می‌شه (پورت ۳۰۰۰).
>
> اصل طلایی کل بک‌اند: **به کلاینت اعتماد نکن.** قیمت، تخفیف، مدت اشتراک، دوره آزمایشی — همه فقط سمت سرور محاسبه و تایید می‌شن.

---

## ۱. نقشه پوشه‌ی `backend/`

```
backend/
├── src/
│   ├── index.ts          ← نقطه استارت سرور
│   ├── app.ts            ← سرهم‌کردن قطعات (مسیرها، CORS، ...)
│   ├── env.ts            ← 📌 لیست همه تنظیمات محیطی
│   ├── db/               ← دیتابیس سرور (جدول‌ها)
│   ├── routes/           ← آدرس‌های API (هر فایل = یک گروه آدرس)
│   ├── services/         ← منطق اصلی (قیمت، اشتراک، کد پیامکی، توکن)
│   ├── providers/        ← اتصال به سرویس‌های بیرونی (پیامک، درگاه)
│   ├── plugins/          ← احراز هویت + مدیریت خطا
│   └── lib/phone.ts      ← ⚠️ قل دومِ استانداردسازی شماره (باید با فرانت یکی باشه)
├── test/                 ← تست‌های خودکار
├── .pglite-data/         ← 💾 دیتابیس توسعه (فایل‌های دیتا — پاکش کنی همه‌چی صفر می‌شه)
└── package.json          ← دستورها: dev, build, start, test
```

## ۲. استارت و تنظیمات

### `backend/src/index.ts` — نقطه شروع

تنها جایی که اتصال واقعی دیتابیس ساخته می‌شه. با توجه به env تصمیم می‌گیره:

- **دیتابیس:** `DB_DRIVER=pglite` (پیش‌فرض توسعه — پستگرس واقعی ولی داخل خود پروسه، بدون نصب هیچی، دیتا در `.pglite-data/`) یا `postgres` (پروداکشن)
- **پیامک:** `SMS_PROVIDER=console` (چاپ کد در ترمینال) یا `kavenegar` (ارسال واقعی)
- **درگاه:** `PSP_PROVIDER=fake` فقط برای توسعه/تست یا `PSP_PROVIDER=zarinpal` برای production. در production فقط زرین‌پال مجاز است.

موقع بالا آمدن: جدول‌ها رو می‌سازه (اگه نباشن)، پلن‌ها رو seed می‌کنه، و هر ۱ ساعت کدهای پیامکی قدیمی‌تر از ۲۴ ساعت رو پاک می‌کنه.

### `backend/src/env.ts` — 📌 همه‌ی تنظیمات محیطی در یک نگاه

| متغیر                | پیش‌فرض                                                  | یعنی                                                                                                                                                                                    |
| -------------------- | -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| `DATABASE_URL`       | `postgres://routino:routino@localhost:5432/routino`      | آدرس پستگرس واقعی                                                                                                                                                                       |
| `CORS_ORIGINS`       | لوکال‌ها + `https://localhost` + `capacitor://localhost` | ⚠️ کدوم آدرس‌ها اجازه دارن به API وصل شن — دو تای آخر برای اپ موبایل **حیاتی**اند                                                                                                       |

| `OTP_MAX_ATTEMPTS`   | `3`                                                      | حداکثر حدس اشتباه برای هر کد                                                                                                                                                            |
| `SMS_PROVIDER`       | `console`                                                | `console` یا `kavenegar`                                                                                                                                                                |
| `KAVENEGAR_API_KEY`  | —                                                        | کلید API کاوه‌نگار                                                                                                                                                                      |
| `KAVENEGAR_TEMPLATE` | `routino-otp`                                            | اسم قالب تاییدشده در پنل کاوه‌نگار                                                                                                                                                      |
| `PSP_PROVIDER`       | `fake`                                                   | `fake` فقط توسعه/تست؛ `zarinpal` تنها مقدار مجاز production                                                                                                                             |
| `ZARINPAL_MERCHANT`  | `dev-only-zarinpal-merchant`                             | مرچنت زرین‌پال (۳۶ نویسه؛ فقط وقتی زرین‌پال فعاله). مقدار پیش‌فرض `dev-only-...` مثل `JWT_SECRET` عمداً با محافظ production قاطی می‌شه — باید حتماً قبل لایو رفتن عوض بشه               |
| `PUBLIC_API_URL`     | `http://localhost:3000`                                  | آدرس عمومی همین سرور (درگاه، مرورگرِ کاربر رو به اینجا برمی‌گردونه — از گوشی باید قابل دسترس باشه)                                                                                      |
| `PUBLIC_WEB_URL`     | `http://localhost:5180`                                  | آدرس نسخه وب اپ (برای برگشت بعد از پرداخت وب)                                                                                                                                           |
| `APP_DEEP_LINK`      | `routino://pay/result`                                   | لینک برگشت به اپ موبایل بعد از پرداخت                                                                                                                                                   |
| `IMPORT_MAX_DAYS`    | `400`                                                    | سقف روزهای قابل قبول موقع انتقال اشتراک قدیمی                                                                                                                                           |

**محافظ‌های پروداکشن (خودکار):** اگه `NODE_ENV=production` باشه و secretها `dev-only` مونده باشن، یا `PSP_PROVIDER=fake` باشه، یا `DB_DRIVER=pglite` باشه → سرور **اصلاً بالا نمیاد**. این عمدیه که با تنظیمات تستی نری روی هوا.

در production هیچ override برای `fake` یا `SMS_PROVIDER=console` وجود ندارد؛ هر دو باعث توقف امن سرویس می‌شوند. مرچنت زرین‌پال هم باید UUID معتبر ۳۶نویسه‌ای باشد.

هر بار که سرور بالا میاد، اگه چیزی تستی باشه با `[!] TEST MODE — …` توی لاگ چاپ می‌شه.

### `backend/src/app.ts` — سرهم‌کننده

Fastify رو می‌سازه، CORS و فشرده‌سازی و helmet رو فعال می‌کنه، مدیریت خطا و پلاگین احراز هویت رو ثبت می‌کنه، و همه‌ی گروه‌های مسیر رو با پیشوند `/v1` رجیستر می‌کنه. هیچ اتصال دیتابیسی اینجا ساخته نمی‌شه (تزریق می‌شه) — همینه که تست‌ها بدون داکر اجرا می‌شن.

## ۴. مسیرهای API — پوشه `backend/src/routes/`

### `backend/src/routes/auth.ts` — ورود با پیامک

| متد و آدرس                     | ورودی                                  | چیکار می‌کنه                                                                                                                                                                         |
| ------------------------------ | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /v1/auth/otp/request`    | `{phone}`                              | چک سقف ارسال ← ساخت کد ۴ رقمی ← ارسال پیامک. جوابش برای شماره‌ی موجود و ناموجود یکسانه (که نشه فهمید کی عضو روتینوئه)                                                                |
| `POST /v1/auth/otp/verify`     | `{phone, code, intent?, newPassword?}` | چک کد ← برای `signup` رمز حساب تازه را ثبت می‌کند؛ برای `password_reset` رمز را عوض می‌کند؛ سپس یک access token سی‌روزه و وضعیت اشتراک را می‌دهد. حساب تازه entitlement=`none` دارد. |

### `backend/src/routes/payments.ts` — 💳 مسیر پول (⚠️ حساس‌ترین فایل بک‌اند)

⚠️ خود `routes/payments.ts` فقط آداپتور نازک Fastify‌ئه (پارس ورودی، رندر پاسخ). **کل منطق پول واقعاً تو `services/payment-flow.ts` زندگی می‌کنه** (بدون وابستگی به فریم‌ورک، عیناً با نسخه‌ی Supabase Edge مشترکه) و صفحه‌ی HTML نتیجه در `lib/pay-result-page.ts` (تابع `renderResultPage`) است. اگه دنبال تغییر رفتار پرداخت اومدی، باید بری سراغ `payment-flow.ts` نه این فایل.

| متد و آدرس                   | چیکار می‌کنه                                                                                                                                                                                                                                  | تابع اصلی در `payment-flow.ts`    |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| `POST /v1/payments/quote`    | پیش‌فاکتور: قیمت پایه + بررسی کد تخفیف. کد نامعتبر = «دلیل» برمی‌گرده نه خطا (که UI پیام درست نشون بده)                                                                                                                                       | (مستقیم از `services/pricing.ts`) |
| `POST /v1/payments/checkout` | ورودی `attemptId` UUID می‌خواهد؛ retry همان خرید همان payment/redirect را می‌گیرد و تماس PSP دوباره ساخته نمی‌شود. مبلغ/ماه/پلن نهایی **سمت سرور** حساب و قبل از I/O ذخیره می‌شوند. سقف ۱۰ خرید در ساعت؛ تخفیف ۱۰۰٪ بدون درگاه                | `checkoutPayment`                 |
| `GET /v1/payments/callback`  | 🌐 فقط `paymentId` + `Authority` + `Status` اسکالر را می‌پذیرد؛ callback مدرک پرداخت نیست. تأیید واقعی فقط Verify سرور-به‌سرور با مبلغ ریالی ذخیره‌شده است. اگر ذخیره Authority قطع شده باشد، فقط Verify موفق اجازه bind و grant اتمیک می‌دهد | `handlePaymentCallback`           |
| `GET /v1/payments/:id`       | استعلام وضعیت برای اپ. **خود-درمانی:** اگه پرداختی در حالت `redirected` گیر کرده (callback هیچ‌وقت نرسیده)، همین‌جا دوباره از درگاه استعلام و در صورت موفقیت فعال می‌شه                                                                       | `pollPayment`                     |

**اعطای اتمیک (`applyPaid`):** درج unique در `grants.payment_id`، افزایش entitlement، audit grant و `payments.applied_at` در یک transaction‌اند. Verify lease دیتابیسی دارد؛ timeout، پاسخ malformed و وضعیت نامشخص terminal نمی‌شوند. کدهای ۱۰۰ و ۱۰۱ زرین‌پال هر دو موفق‌اند و callback/poll هم‌زمان فقط یک grant می‌سازند.

## ۵. منطق اصلی — پوشه `backend/src/services/`

### `backend/src/services/entitlement.ts` — حساب‌وکتاب اشتراک

- `readEntitlement` — جواب فعلی: `active` / `expired` / `none` + تاریخ انقضا
- `grantInterval` — تمدید با **ماه تقویمی واقعی** (پستگرس حساب می‌کنه؛ «یک سال» = ۱۲ ماه واقعی نه ۳۶۰ روز). اگه اشتراک هنوز فعاله، از انتهای همون ادامه می‌ده (زودتر خریدن = روز نمی‌سوزه). هر تمدید یک سطر در دفترکل `grants` ثبت می‌کنه
- `startTrialOnce` — داخل transaction ردیف user را قفل می‌کند؛ وجود هر grant قبلی یا حتی entitlement بدون ledger را رد می‌کند و فقط برای حساب کاملاً بدون سابقه، دقیقاً ۷ روز `trial` می‌دهد
- `ensureExpiresAt` — مخصوص انتقال اشتراک قدیمی: فقط «بالا می‌بره تا»، هیچ‌وقت جمع نمی‌زنه
- `hasSettledGrant` — «این حساب قبلاً پرداخت یا انتقال داشته؟» (قفل تکرار import)

### `backend/src/services/pricing.ts` — قیمت

- `quote` — قیمت نهایی: پایه ← اِعمال آفر ← اِعمال تخفیف ← گرد کردن. تبدیل تومان→ریال (×۱۰) **فقط همین‌جاست**

### `backend/src/services/tokens.ts` — توکن‌ها

### `backend/src/services/sync.ts` — sync فعالِ دادهٔ شخصی

- مسیر اصلی `POST /v1/sync/exchange` در یک invocation ابتدا زیر همان قفل owner مطمئن می‌شود cursor از `gc_seq` عقب نیست، بعد dirty rowها را push و از cursor قبلی pull می‌کند. اگر cursor عقب باشد هیچ ردیفی نوشته نمی‌شود و پاسخ `reset=true, batchAccepted=false` است. مسیرهای قدیمی push/pull فعلاً برای تست/سازگاری باقی‌اند، ولی push بدون cursor پس از اولین GC آن حساب عمداً non-2xx می‌دهد تا outbox کلاینت قدیمی پاک نشود. اشتراک هرگز شرط sync نیست.
- kindهای عمومی پروتکل ۲ دقیقاً `categories`، `habits`، `habitMonths`، `tasks`، `timerSessions` و `journal` هستند؛ `taskMonths` فقط نمایش داخلی دیتابیس برای کارهای تکمیل‌شدهٔ قدیمی است و پیش از خروج API به همان `tasks` معمولی باز می‌شود. `logs` فقط مدل روزانهٔ IndexedDB است و تنظیمات همگی local-only هستند. exchange بدون `protocolVersion: 2` رد می‌شود.
- هر `habitMonths` حداکثر ۳۱ سلول روزِ تخت و bounded دارد. push می‌تواند فقط روزهای dirty را بفرستد؛ SQL همان سلول‌ها را با timestamp مستقل داخل ماه کامل merge می‌کند. بنابراین روز جدید با envelope قدیمی‌تر هم گم نمی‌شود، replay مساوی seq ردیف را عوض نمی‌کند و حذف عادت به‌جای صدها روز فقط ماه‌های همان عادت را tombstone می‌کند.
- `sync-record-validation.ts` شکل دقیق هر kind، کلید طبیعی، enumها، عددهای finite، طول رشته و حجم واقعی UTF-8 را قبل از نوشتن بررسی می‌کند. ژورنال حداکثر ۴۰۰۰ کاراکتر و ۱۶ KiB متن UTF-8 دارد؛ packet ماه سقف ۴۴ KiB و بقیهٔ رکوردهای زنده سقف ۲۰ KiB دارند. `data: unknown` دیگر به معنی JSON دلخواه نیست.
- رد semantic به‌صورت `rejectedRecords` و بدون بازتاب متن/دادهٔ خصوصی برمی‌گردد؛ رکوردهای سالم همان batch همچنان ذخیره و pull می‌شوند. فقط envelope خراب یا بیش از ۲۰۰ رکورد، خطای کل درخواست است.
- برای هر حساب سقف سخت ۵۰٬۰۰۰ ردیف کلادی (با tombstone) باقی است. `sync_data_bytes` هنوز شمارندهٔ دقیق و غیرمنفی حجم جاری است، اما سقف مادام‌العمر ۱۲۸ MiB حذف شده. به‌جایش هر دورهٔ ۳۶۵روزهٔ حساب حداکثر ۱۰ MiB **رشد مثبت JSON** می‌پذیرد؛ کم‌کردن حجم یا حذف چیزی سهمیه را پس نمی‌دهد. دادهٔ موجود هنگام migration دست‌نخورده و grandfathered است و مصرف دورهٔ تازه از صفر شروع می‌شود.
- اگر یک رکورد سالم از سهمیه عبور کند، همان نسخه با metadata محدود `account_quota_exceeded` و `retryAt` رد می‌شود و pull و رکوردهای قابل‌قبول دیگر ادامه دارند. رد رشد سالانه موعد دقیق پایان دوره دارد؛ رد سقف ۵۰٬۰۰۰ ردیف موعد محدود یک‌روزه دارد، نه تاریخ سالانه. کلاینت آن نسخه را با `dirty: 2` تا موعد نگه می‌دارد؛ این حالت انتظار محلی است، نه حذف داده، و متن ژورنال یا payload خصوصی هرگز echo نمی‌شود.
- `routino_compact_task_months` فقط task تکمیل‌شده‌ای را برمی‌دارد که هم پایان ماهش حداقل ۷ روز گذشته و هم آخرین ویرایشش حداقل ۷ روز قدیمی است. archive تغییرناپذیر است؛ ویرایش/حذف جدید به‌صورت task معمولی و جدیدتر روی آن غلبه می‌کند. wrapper زمان‌بندی‌شده advisory lock می‌گیرد، هر دقیقه حداکثر ۱٬۰۰۰ source task را در دو chunk تأییدشدهٔ ۵۰۰تایی پردازش می‌کند و وقتی backlog خالی است هیچ جدول product/temp را تغییر نمی‌دهد. cron با `statement_timeout=45s` و `lock_timeout=1s` محدود است و overlap با advisory lock رد می‌شود. ظرفیت ۱٬۴۴۰٬۰۰۰ task در روز فقط سقف نظریِ schedule×batch و fixture محلی شاهد losslessness است؛ throughput واقعی یا غلبه بر arrival را تضمین نمی‌کند. `routino_task_compaction_backlog` تعداد دقیق task واجدشرایط، owner-monthها و قدیمی‌ترین `updated_at` را read-only گزارش می‌کند. همهٔ این کارها داخل Postgres و با **صفر درخواست اپلیکیشن/Edge** انجام می‌شود. نمودار، جست‌وجو، Export و آفلاین همچنان روی taskهای فردی محلی کار می‌کنند.
- tombstoneهای قدیمی‌تر از ۹۰ روز با `routino_purge_tombstones` و index جزئیِ `updated_at, seq` هر ۵ دقیقه در batch حداکثر ۲٬۰۰۰تایی پاک می‌شوند. cron آن هم `statement_timeout=45s` و `lock_timeout=1s` دارد و overlap نمی‌کند. owner پیش از ردیف tombstone با `SKIP LOCKED` قفل می‌شود؛ حذف و بالا بردن `gc_seq` هر کاربر در همان تراکنش انجام می‌شود، و gate نوشتن exchange نیز همان owner را قفل می‌کند. پس کلاینت عقب‌مانده قبل از هر write پاسخ reset می‌گیرد و دادهٔ حذف‌شده زنده نمی‌شود. ردیف live و tombstone جدید دست‌نخورده می‌مانند.
- پاک‌سازی حساب فقط allow-list است: حساب بدون grant/entitlement یا دقیقاً یک تریال ۷روزهٔ سازگار، بدون هیچ payment، grant غیرتریال، redemption یا discount استفاده‌شده/referenced. موعد عادی `max(created_at + 30 days, trial expiry)` است؛ برای کاربران قبل از migration یک کف یک‌بارهٔ `deployTime + 30 days` ثبت می‌شود. تابع روزانه batch=50 با `SKIP LOCKED` و timeout کوتاه اجرا می‌شود؛ cascade موجود `records` شامل `taskMonths` است و triggerهای quota قرارداد فعلی را حفظ می‌کنند.
- `anonymous_counters` فقط عدد مادام‌العمر `trial_starts` را نگه می‌دارد. retry تریال دوباره شمرده نمی‌شود و phone/userId/IP/hash ندارد. این شمارنده فقط یک متریک اضافه است: فهرست، جستجو و جزئیات ادمین همهٔ حساب‌های موجود، از جمله registration-only و trial-only فعال/منقضی را مثل قبل نمایش می‌دهد تا اعطای grant ادمین ممکن بماند؛ فقط حذف واقعی ردیف `users` حساب را از پنل خارج می‌کند.
- pull برای هر صفحه یک query مالک+رکورد دارد: حداکثر prefix خام ۲۵۶ KiB و فقط یک lookahead archive می‌خواند، سپس archive را کامل و bounded به task معمولی باز می‌کند. این حد فشار DB/Edge است؛ اندازه‌گیری‌های fixture وعدهٔ ظرفیت provider یا تعداد کاربر نیستند.
- در پنجرهٔ rollout قدیمی، fallback writer فقط برای exchange با cursor صفر و خطای دقیق نبودن `routino_sync_push_if_current(` یا writer پایه فعال می‌شود؛ cursor غیرصفر و push قدیمیِ بدون cursor fail-closed می‌شوند. پس rollout ممکن است موقتاً retry بسازد، اما outbox ذخیره‌شده را تسویه یا حذف نمی‌کند.
- client با cursor-gate-before-push، LWW بر اساس `updatedAt`، clamp ساعت، tombstone، pagination، GC reset و تسویهٔ مستقل هر رکورد کار می‌کند. `batchAccepted=false` یعنی dirty flag هیچ عضو آن batch نباید پاک شود؛ reset فقط نسخه‌های synced را پاک می‌کند و سپس pull از صفر انجام می‌شود.
- صفحهٔ نهایی pull entitlement را هم برمی‌گرداند تا کاربرِ منقضی هم بتواند تاریخچه‌اش را بازیابی کند.
- Fastify و Hono/Edge هر دو JSON را پیش از parse روی ۶۴ KiB می‌بندند؛ Hono علاوه بر `Content-Length`، stream واقعی را هم بایت‌به‌بایت محدود می‌کند تا هدر حذف‌شده یا دروغین راه دورزدن نباشد.

> ترتیب rollout امن: ابتدا کد fail-closed deploy می‌شود؛ روی schema قدیمی فقط exchange تازه با cursor صفر fallback دارد و بقیهٔ pushها تا migration retry می‌شوند، بدون پاک‌شدن outbox. سپس backup، dry-run و canary read-only انجام می‌شود و migration افزایشی `20260905140000_elastic_launch_hardening.sql` gate/index/functionها و scheduleهای bounded را نصب می‌کند، اما هنگام migration هیچ compaction/purgeای روی دادهٔ موجود اجرا نمی‌کند. چون scheduleها را فعال می‌کند، اجرای آن همچنان مجوز جداگانهٔ production می‌خواهد؛ canary کامل sync بعد از migration انجام می‌شود.

### `backend/src/services/payment-flow.ts` — 💳 ماشین حالت پرداخت (منطق واقعی مسیر پول)

- `checkoutPayment` / `handlePaymentCallback` / `pollPayment` / `applyPaid` — همون‌هایی که بالاتر تو جدول `routes/payments.ts` بهشون اشاره شد. عیناً (بدون تغییر) با `supabase/functions/api/shared/` سینک می‌شه؛ تست parity جلوی جدایی رو می‌گیره.

### `backend/src/services/admin.ts` — منطق API های پنل ادمین

- `adminOverview`, `adminListUsers`, `adminUserDetail`, `adminGrant`, `adminListPayments`, `adminListDiscounts`, `adminCreateDiscount`, `adminUpdateDiscount` — همه‌ی چیزی که `routes/admin.ts` صداشون می‌زنه
- `adminOverview` همهٔ عددهای نمای کلی را با **یک درخواست API و یک دستور SQL تجمیعی** می‌خواند؛ جدول کاربران، اشتراک‌ها، پرداخت‌ها و OTP هرکدام حداکثر یک‌بار در همان دستور اسکن می‌شوند و fan-out چند query وجود ندارد.
- بعد از تأیید OTP، پوستهٔ پنل فوراً باز می‌شود و منتظر آمار نمی‌ماند. فقط عددهای کلی نمای قبلی در `sessionStorage` همان تب نگه داشته می‌شوند و پس از معتبرشدن cookie در پس‌زمینه با یک درخواست تازه می‌شوند؛ شمارهٔ کاربران، ردیف پرداخت/تخفیف، OTP، CSRF و secret هیچ‌وقت cache نمی‌شوند.
- پنل polling و retry خودکار ندارد. تب‌های کاربران، پرداخت‌ها و تخفیف‌ها فقط هنگام بازشدن خودشان request می‌زنند؛ overview هم هنگام ورود، تازه‌سازی صریح یا تغییر مرتبط خوانده می‌شود. request معلق بعد از timeout متوقف می‌شود تا loop و فشار پنهان نسازد.

## ۱۰. ⚠️ چیزهایی که در بک‌اند دست نزنی مگر با فهم کامل

1. **`services/payment-flow.ts`** (نه `routes/payments.ts`) — منطق `applied_at` و مقایسه مبلغ. جابه‌جایی یک شرط = یا دوباره‌شارژ مفتی یا سوختن پول کاربر.
2. **`lib/phone.ts`** — باید بایت‌به‌بایت با `src/lib/phone.ts` فرانت یکی بمونه (تست parity داره).
3. **`services/entitlement.ts`** — تنها نویسنده‌ی `entitlements`؛ دفترکل `grants` هیچ‌وقت ویرایش نمی‌شه.
4. **ترتیب چک‌ها در `services/otp.ts`** — «تلاش قبل از مقایسه شمرده می‌شه» عمدیه (کرش وسط کار = حدس مفتی نده).
5. **`env.ts` محافظ‌های production** — حذفشون نکن؛ همونان که نمی‌ذارن با تنظیمات تستی لایو بری.
