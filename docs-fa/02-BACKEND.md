# 🖥️ راهنمای کامل بک‌اند روتینو

> **بک‌اند یعنی چی؟** سروری که جدا از اپ اجرا می‌شه و کارهایی رو انجام می‌ده که نباید دست کاربر باشه: ورود با پیامک، حساب‌وکتاب اشتراک، پرداخت با درگاه، و پنل مدیریت.
> همه‌ی بک‌اند داخل پوشه‌ی **`backend/`** است و کاملاً مستقل از فرانت اجرا می‌شه (پورت ۳۰۰۰).
>
> اصل طلایی کل بک‌اند: **به کلاینت اعتماد نکن.** قیمت، تخفیف، مدت اشتراک، دوره آزمایشی — همه فقط سمت سرور محاسبه و تایید می‌شن.

---

## ۱. نقشه پوشه‌ی `backend/`

```
backend/
├── src/
│   ├── index.ts          ← نقطه استارت سرور
│   ├── app.ts            ← سرهم‌کردن قطعات (مسیرها، CORS، ...)
│   ├── env.ts            ← 📌 لیست همه تنظیمات محیطی
│   ├── db/               ← دیتابیس سرور (جدول‌ها)
│   ├── routes/           ← آدرس‌های API (هر فایل = یک گروه آدرس)
│   ├── services/         ← منطق اصلی (قیمت، اشتراک، کد پیامکی، توکن)
│   ├── providers/        ← اتصال به سرویس‌های بیرونی (پیامک، درگاه)
│   ├── plugins/          ← احراز هویت + مدیریت خطا
│   └── lib/phone.ts      ← ⚠️ قل دومِ استانداردسازی شماره (باید با فرانت یکی باشه)
├── test/                 ← تست‌های خودکار
├── .pglite-data/         ← 💾 دیتابیس توسعه (فایل‌های دیتا — پاکش کنی همه‌چی صفر می‌شه)
└── package.json          ← دستورها: dev, build, start, test
```

## ۲. استارت و تنظیمات

### `backend/src/index.ts` — نقطه شروع

تنها جایی که اتصال واقعی دیتابیس ساخته می‌شه. با توجه به env تصمیم می‌گیره:

- **دیتابیس:** `DB_DRIVER=pglite` (پیش‌فرض توسعه — پستگرس واقعی ولی داخل خود پروسه، بدون نصب هیچی، دیتا در `.pglite-data/`) یا `postgres` (پروداکشن)
- **پیامک:** `SMS_PROVIDER=console` (چاپ کد در ترمینال) یا `kavenegar` (ارسال واقعی)
- **درگاه:** `PSP_PROVIDER=fake` (درگاه تقلبی تست) یا `zibal` (واقعی)

موقع بالا آمدن: جدول‌ها رو می‌سازه (اگه نباشن)، پلن‌ها رو seed می‌کنه، و هر ۱ ساعت کدهای پیامکی قدیمی‌تر از ۲۴ ساعت رو پاک می‌کنه.

### `backend/src/env.ts` — 📌 همه‌ی تنظیمات محیطی در یک نگاه

| متغیر                      | پیش‌فرض                                                  | یعنی                                                                                                                                                                                    |

| `SMS_PROVIDER`             | `console`                                                | `console` یا `kavenegar`                                                                                                                                                                |
| `KAVENEGAR_API_KEY`        | —                                                        | کلید API کاوه‌نگار                                                                                                                                                                      |

| `ZIBAL_RELAY_SECRET`       | —                                                        | secret امضای HMAC رله (حداقل ۳۲ کاراکتر و دقیقاً یکسان با مقدار روی رله)                                                                                                                |
| `ZARINPAL_MERCHANT`        | `dev-only-zarinpal-merchant`                             | مرچنت زرین‌پال (۳۶ نویسه؛ فقط وقتی زرین‌پال فعاله). مقدار پیش‌فرض `dev-only-...` مثل `ADMIN_TOKEN`/`JWT_SECRET` عمداً با محافظ production قاطی می‌شه — باید حتماً قبل لایو رفتن عوض بشه |
| `PUBLIC_API_URL`           | `http://localhost:3000`                                  | آدرس عمومی همین سرور (درگاه، مرورگرِ کاربر رو به اینجا برمی‌گردونه — از گوشی باید قابل دسترس باشه)                                                                                      |
| `PUBLIC_WEB_URL`           | `http://localhost:5180`                                  | آدرس نسخه وب اپ (برای برگشت بعد از پرداخت وب)                                                                                                                                           |
| `APP_DEEP_LINK`            | `routino://pay/result`                                   | لینک برگشت به اپ موبایل بعد از پرداخت                                                                                                                                                   |
| `IMPORT_MAX_DAYS`          | `400`                                                    | سقف روزهای قابل قبول موقع انتقال اشتراک قدیمی                                                                                                                                           |
| **`ALLOW_TEST_PROVIDERS`** | `false`                                                  | ⚠️ اجازه‌ی صریح برای موندن روی **سندباکس زیبال** و/یا **پیامک کنسولی** در پروداکشن. بدون این، سرور با اون تنظیمات بالا نمیاد. وقتی مرچنت واقعی و کاوه‌نگار وصل شد، **حذفش کن**          |

**محافظ‌های پروداکشن (خودکار):** اگه `NODE_ENV=production` باشه و secretها `dev-only` مونده باشن، یا `PSP_PROVIDER=fake` باشه، یا `DB_DRIVER=pglite` باشه → سرور **اصلاً بالا نمیاد**. این عمدیه که با تنظیمات تستی نری روی هوا.

از این هم بالا نمیاد (اضافه‌شده): **`ZIBAL_MERCHANT=zibal`** (سندباکس) یا **`SMS_PROVIDER=console`** در پروداکشن — مگه اینکه `ALLOW_TEST_PROVIDERS=true` بذاری. دلیلش: سندباکس زیبال هیچ فرقی در ظاهر نداره؛ کاربر صفحه‌ی درگاه واقعی می‌بینه، «پرداخت موفق» می‌گیره، اشتراک واقعی هم می‌گیره — ولی **یک ریال به حسابت نمی‌رسه**. تنها چیزی که جلوی این رو می‌گیره همین محافظه.

هر بار که سرور بالا میاد، اگه چیزی تستی باشه با `[!] TEST MODE — …` توی لاگ چاپ می‌شه.

### `backend/src/app.ts` — سرهم‌کننده

Fastify رو می‌سازه، CORS و فشرده‌سازی و helmet رو فعال می‌کنه، مدیریت خطا و پلاگین احراز هویت رو ثبت می‌کنه، و همه‌ی گروه‌های مسیر رو با پیشوند `/v1` رجیستر می‌کنه. هیچ اتصال دیتابیسی اینجا ساخته نمی‌شه (تزریق می‌شه) — همینه که تست‌ها بدون داکر اجرا می‌شن.

## ۴. مسیرهای API — پوشه `backend/src/routes/`

### `backend/src/routes/auth.ts` — ورود با پیامک

| متد و آدرس                    | ورودی                       | چیکار می‌کنه                                                                                                              |
| ----------------------------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `POST /v1/auth/otp/request`   | `{phone}`                   | چک سقف ارسال ← ساخت کد ۴ رقمی ← ارسال پیامک. جوابش برای شماره‌ی موجود و ناموجود یکسانه (که نشه فهمید کی عضو روتینوئه)     |
| `POST /v1/auth/otp/verify`    | `{phone, code, deviceName}` | چک کد ← اگه کاربر جدیده: ساخت حساب + **۷ روز هدیه** (ثابت `TRIAL_DAYS = 7` بالای همین فایل) ← صدور توکن‌ها + وضعیت اشتراک |
| `POST /v1/auth/token/refresh` | `{refresh}`                 | توکن تازه می‌ده؛ توکن قبلی همون لحظه می‌میره                                                                              |
| `POST /v1/auth/logout`        | `{refresh}`                 | خروج این دستگاه (توکن ناشناس هم ۲۰۰ می‌گیره — بی‌ضرره)                                                                    |

### `backend/src/routes/payments.ts` — 💳 مسیر پول (⚠️ حساس‌ترین فایل بک‌اند)

⚠️ خود `routes/payments.ts` فقط آداپتور نازک Fastify‌ئه (پارس ورودی، رندر پاسخ). **کل منطق پول واقعاً تو `services/payment-flow.ts` زندگی می‌کنه** (بدون وابستگی به فریم‌ورک، عیناً با نسخه‌ی Supabase Edge مشترکه) و صفحه‌ی HTML نتیجه در `lib/pay-result-page.ts` (تابع `renderResultPage`) است. اگه دنبال تغییر رفتار پرداخت اومدی، باید بری سراغ `payment-flow.ts` نه این فایل.

| متد و آدرس                   | چیکار می‌کنه                                                                                                                                                                                                                                                                                                                                                      | تابع اصلی در `payment-flow.ts`    |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| `POST /v1/payments/quote`    | پیش‌فاکتور: قیمت پایه + بررسی کد تخفیف. کد نامعتبر = «دلیل» برمی‌گرده نه خطا (که UI پیام درست نشون بده)                                                                                                                                                                                                                                                           | (مستقیم از `services/pricing.ts`) |
| `POST /v1/payments/checkout` | ساخت سطر پرداخت (مبلغ **سمت سرور** حساب می‌شه) ← ثبت در درگاه ← برگردوندن `paymentUrl`. سقف ۱۰ خرید در ساعت برای هر کاربر. تخفیف ۱۰۰٪ = بدون درگاه، مستقیم فعال می‌شه                                                                                                                                                                                             | `checkoutPayment`                 |
| `GET /v1/payments/callback`  | 🌐 مرورگرِ کاربر بعد از درگاه به اینجا برمی‌گرده. `success=1` توی آدرس **هیچ ارزشی نداره** (هرکی می‌تونه تایپش کنه) — تایید واقعی فقط با تماس سرور-به-سرور (`psp.verify`) انجام می‌شه و **مبلغِ تاییدشده باید دقیقاً با مبلغ ما برابر باشه** وگرنه `verify_failed` + لاگ اضطراری. بعدش صفحه HTML نتیجه رو نشون می‌ده که کاربر رو به وب یا دیپ‌لینک اپ برمی‌گردونه | `handlePaymentCallback`           |
| `GET /v1/payments/:id`       | استعلام وضعیت برای اپ. **خود-درمانی:** اگه پرداختی در حالت `redirected` گیر کرده (callback هیچ‌وقت نرسیده)، همین‌جا دوباره از درگاه استعلام و در صورت موفقیت فعال می‌شه                                                                                                                                                                                           | `pollPayment`                     |

**قفل ضد دوباره‌شارژ (`applyPaid` در `services/payment-flow.ts`):** فعال‌سازی فقط با `UPDATE ... WHERE applied_at IS NULL` انجام می‌شه — یعنی حتی اگه درگاه ۱۰ بار callback بزنه یا کاربر ۱۰ بار رفرش کنه، اشتراک فقط **یک بار** اضافه می‌شه. اگه وسط کار خطا بخوره، قفل آزاد می‌شه که تلاش بعدی جبران کنه (پولِ داده‌شده هیچ‌وقت نباید بسوزه).

### `backend/src/routes/subscriptions.ts` — اشتراک

| متد و آدرس                      | چیکار می‌کنه                                                                                                                                                                                                                       |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /v1/subscriptions/me`      | «تا کِی دسترسی دارم؟» — فرانت اول هر اجرا اینو می‌پرسه                                                                                                                                                                             |

## ۵. منطق اصلی — پوشه `backend/src/services/`

### `backend/src/services/entitlement.ts` — حساب‌وکتاب اشتراک

- `readEntitlement` — جواب فعلی: `active` / `expired` / `none` + تاریخ انقضا
- `grantInterval` — تمدید با **ماه تقویمی واقعی** (پستگرس حساب می‌کنه؛ «یک سال» = ۱۲ ماه واقعی نه ۳۶۰ روز). اگه اشتراک هنوز فعاله، از انتهای همون ادامه می‌ده (زودتر خریدن = روز نمی‌سوزه). هر تمدید یک سطر در دفترکل `grants` ثبت می‌کنه
- `ensureExpiresAt` — مخصوص انتقال اشتراک قدیمی: فقط «بالا می‌بره تا»، هیچ‌وقت جمع نمی‌زنه
- `hasSettledGrant` — «این حساب قبلاً پرداخت یا انتقال داشته؟» (قفل تکرار import)

### `backend/src/services/pricing.ts` — قیمت

- `quote` — قیمت نهایی: پایه ← اِعمال آفر ← اِعمال تخفیف ← گرد کردن. تبدیل تومان→ریال (×۱۰) **فقط همین‌جاست**
- `checkDiscount` — همه دلایل رد کد: ناشناخته/غیرفعال/منقضی/ظرفیت‌تمام/مال یکی دیگه/قبلاً استفاده‌شده
- `redeemDiscount` — مصرف کد؛ فقط **بعد از** موفقیت پرداخت صدا زده می‌شه (خرید نصفه‌کاره کد رو نمی‌سوزونه)

### `backend/src/services/otp.ts` — کدهای پیامکی

- کد: ۴ رقمی از مولد امن؛ فقط هَشِ نمک‌دارش ذخیره می‌شه؛ ۲ دقیقه اعتبار؛ ۵ حدس؛ فقط جدیدترین کد معتبره (درخواست کد جدید = ابطال قبلی)
- 💸 **سقف‌های ارسال (`LIMITS`)** — هر پیامک پول واقعیه:

| سقف               | مقدار                                                           |
| ----------------- | --------------------------------------------------------------- |
| هر شماره در دقیقه | ۱                                                               |
| هر شماره در ساعت  | ۵                                                               |
| هر شماره در روز   | ۱۰                                                              |
| هر IP در ساعت     | ۲۰                                                              |
| کل سیستم در روز   | ۲۰۰۰ (کلید قطع اضطراری — اگه خورد یعنی یه اتفاق غیرعادی افتاده) |

### `backend/src/services/tokens.ts` — توکن‌ها

- **Access:** JWT امضاشده، پیش‌فرض ۱ ساعت؛ middleware در هر درخواست خصوصی علاوه بر JWT ردیف دستگاه/کاربر را چک می‌کند، بنابراین افزایش عمر JWT باعث تأخیر در ابطال دستگاه نمی‌شود
- **Refresh:** رشته تصادفی مات، ۱۸۰ روز، با هر استفاده **عوض می‌شه** (قبلی می‌میره)، قابل ابطال (بلاک کاربر = ابطال همه دستگاه‌ها با `revokeAllDevices`)
- **سقف دستگاه:** پیش‌فرض ۱ و از پنل ادمین برای هر حساب ۱ تا ۱۰. ورود نصب تازه در ظرفیت پر، کم‌فعال‌ترین دستگاه را با دلیل `device_replaced` باطل می‌کند.
  - سه جایگزینی در ۱۵ روز rolling مجاز است؛ چهارمی حساب را با `device_security_locked` قفل می‌کند. ادمین می‌تواند سقف، شمارنده و قفل را مدیریت کند.
  - کلاینت روی boot/online/foreground و هر ۶۰ ثانیهٔ foreground بررسی می‌کند. آفلاین حداکثر ۱۵ روز lease دارد؛ بعد از آن فقط تأیید آنلاین لازم است و دیتای محلی پاک نمی‌شود.
  - تست‌ها: `backend/test/device-security.test.ts`، `devices.test.ts` و `src/lib/security-session.test.ts`.

### `GET /v1/devices/ping` — بررسی کم‌هزینهٔ امنیت

- فقط اعتبار کاربر/دستگاه را در middleware بررسی می‌کند و `{ok:true}` می‌دهد؛ entitlement یا لیست دستگاه‌ها را دوباره نمی‌خواند.
- کلاینت در boot، online، foreground و هر ۶۰ ثانیهٔ foreground از این مسیر استفاده می‌کند.
- refresh کامل entitlement در حالت عادی هر ۶ ساعت و در سه روز پایانی هر ۱ ساعت انجام می‌شود. همان refresh پرداخت‌های callback‌گم‌شده را هم به‌صورت idempotent ترمیم می‌کند.

### `backend/src/services/sync.ts` — فقط کد میراثی

- کلاینت آن را import/اجرا نمی‌کند و routeهای واقعی قبل از رسیدن به service با `410 sync_disabled` متوقف می‌شوند.
- `LEGACY_PERSONAL_SYNC_ENABLED=true` فقط در تست/توسعه برای اجرای تست‌های سازگاری قدیمی مجاز است و در production خطای boot می‌دهد.
- بعد از استقرار این نسخه، جدول `records` باید شمارش و سپس در یک تراکنش پاک شود.

### `backend/src/services/payment-flow.ts` — 💳 ماشین حالت پرداخت (منطق واقعی مسیر پول)

- `checkoutPayment` / `handlePaymentCallback` / `pollPayment` / `applyPaid` — همون‌هایی که بالاتر تو جدول `routes/payments.ts` بهشون اشاره شد. عیناً (بدون تغییر) با `supabase/functions/api/shared/` سینک می‌شه؛ تست parity جلوی جدایی رو می‌گیره.

### `backend/src/services/admin.ts` — منطق API های پنل ادمین

- `adminOverview`, `adminListUsers`, `adminUserDetail`, `adminSetBlocked`, `adminGrant`, `adminListPayments`, `adminListDiscounts`, `adminCreateDiscount`, `adminUpdateDiscount` — همه‌ی چیزی که `routes/admin.ts` صداشون می‌زنه
