# طراحی آمادگی لانچ: دادهٔ محلی پایدار، امنیت دستگاه و PWA آفلاین

**تاریخ:** ۲۰۲۶-۰۸-۱۸  
**وضعیت:** تأییدشده برای اجرا  
**محصول:** Routino (وب PWA و اپ Capacitor)

## ۱. هدف و مرز پروژه

Routino باید یک اپ local-first واقعی باشد: عادت‌ها، گزارش‌ها، کارها، تایمر، ژورنال و تنظیمات شخصی فقط روی دستگاه کاربر ذخیره می‌شوند و برای استفادهٔ روزمره به اینترنت وابسته نیستند. سرور فقط هویت حساب، دستگاه‌ها، رویدادهای امنیتی، نشست‌ها، اشتراک، پرداخت، OTP، داده‌های پنل ادمین و بازخوردی را که کاربر صریحاً ارسال می‌کند نگه می‌دارد.

این تغییر هم‌زمان چهار مسئله را حل می‌کند:

1. جلوگیری از استفادهٔ هم‌زمان چند نفر از یک حساب با دیتاست‌های محلی متفاوت؛
2. جلوگیری از حذف ناخواستهٔ اطلاعات محلی هنگام خروج یا تعویض حساب؛
3. حفظ عملکرد کامل وب‌اپ در اینترنت ضعیف، VPN و حالت آفلاین؛
4. ساخت تجربهٔ شفاف برای دستگاه‌ها، اعلان‌ها، پشتیبان‌گیری و پایان اشتراک.

## ۲. تصمیم‌های قطعی محصول

- سقف دستگاه فعال هر حساب به‌صورت پیش‌فرض `1` است.
- ادمین می‌تواند سقف دستگاه فعال هر کاربر را در بازهٔ `1..10` تغییر دهد.
- ورود همان حساب از دستگاه جدید، در صورت پر بودن ظرفیت، قدیمی‌ترین نشست فعال را باطل می‌کند.
- ورود مجدد از همان دستگاه، تمدید توکن و نصب نسخهٔ جدید برنامه «تعویض دستگاه» نیست.
- هر حساب در یک بازهٔ شناور ۳۰روزه سه تعویض مجاز دارد؛ تعویض چهارم حساب را با عنوان محترمانهٔ «قفل امنیتی» مسدود و همهٔ نشست‌ها را باطل می‌کند.
- اگر سقف دستگاه حساب بیشتر از یک باشد، پر کردن ظرفیت خالی تعویض محسوب نمی‌شود؛ فقط جایگزینی دستگاه بعد از پر شدن ظرفیت شمارش می‌شود.
- ادمین می‌تواند سقف دستگاه، قفل امنیتی و شمارندهٔ تعویض را مشاهده، بازنشانی و مدیریت کند.
- راه ارتباط هنگام قفل امنیتی `@routino_support` است.
- اعتبار آفلاین حساب حداکثر ۱۵ روز از آخرین تأیید موفق سرور است. پس از آن برنامه برای بازکردن فضای حساب به یک اتصال کوتاه نیاز دارد، اما هیچ داده‌ای حذف نمی‌شود.
- Export برای Trial، رایگان و پولی همیشه فعال است.
- Import برای Trial/رایگان ممنوع و فقط برای اشتراک پولی فعال است. این محدودیت هم در رابط و هم در منطق اصلی اعمال می‌شود.
- سه روز قبل از پایان اشتراک و هنگام پایان اشتراک، اعلان درون‌برنامه‌ای ساخته می‌شود؛ اعلان سیستمی نیز در صورت داشتن مجوز زمان‌بندی می‌شود.
- دادهٔ شخصی موجود در جدول سروری `records` بعد از عبور کد جدید از تست‌ها پاک می‌شود و مسیرهای sync دادهٔ شخصی از API خارج می‌شوند.

## ۳. معماری دادهٔ محلی

### ۳.۱ خزانهٔ جدا برای هر حساب

یک دیتابیس مشترک بدون جداسازی مالک قابل قبول نیست، چون خروج کاربر A و ورود کاربر B روی همان مرورگر می‌تواند اطلاعات A را به B نشان دهد. هر حساب یک `vaultId` پایدار می‌گیرد:

- حساب واردشده: مشتق‌شده از شناسهٔ کاربر سرور، نه شمارهٔ خام؛
- حالت مهمان/قبل از ورود: شناسهٔ محلی نصب؛
- نگاشت حساب به vault فقط روی همان دستگاه نگه‌داری می‌شود.

IndexedDB هر vault نام مستقل دارد یا تمام کلیدها با vault namespace می‌شوند. تعویض حساب فقط vault فعال را عوض می‌کند. خروج، revocation، پایان اشتراک، قفل امنیتی و خطای شبکه هیچ‌گاه جدول‌های داده را پاک نمی‌کنند.

عملیات حذف داده فقط از مسیر صریح «حذف اطلاعات این دستگاه» با تأیید دوباره انجام می‌شود و دقیقاً همان vault انتخاب‌شده را هدف می‌گیرد.

### ۳.۲ دوام و مهاجرت

- IndexedDB مرجع اصلی دادهٔ ساختاریافته است.
- `navigator.storage.persist()` در HTTPS درخواست می‌شود و نتیجه در وضعیت سلامت حافظه نمایش داده می‌شود.
- نصب PWA به‌عنوان راه افزایش دوام حافظه پیشنهاد می‌شود.
- مهاجرت schema افزایشی و تراکنشی است؛ هیچ upgradeای حق `deleteDatabase` یا پاک‌کردن جدول موجود را ندارد.
- blob قدیمی `routino:v1` تا تأیید موفق مهاجرت حفظ می‌شود.
- خطای quota، خرابی migration یا قطع‌شدن برنامه باید پیام قابل‌فهم بدهد و نسخهٔ قبلی را قابل‌خواندن نگه دارد.
- پاک‌کردن دستی Site Data، حذف Browser Profile یا پاک‌شدن سیستم‌عامل خارج از کنترل برنامه است؛ برای همین Export دائمی و یادآوری پشتیبان ضروری است.

### ۳.۳ Backup

- Export شامل دادهٔ کاربردی vault و نسخهٔ schema است.
- Export شامل access token، refresh token، رمز، OTP، اطلاعات پرداخت یا اسرار اشتراک نیست.
- Import ابتدا فایل را parse و validate می‌کند، نسخه و اندازه را می‌سنجد، سپس در یک تراکنش merge/restore می‌کند.
- Import برای trial/free قبل از بازکردن file picker و دوباره قبل از commit تراکنش رد می‌شود تا دورزدن UI ممکن نباشد.
- فایل خراب یا نسخهٔ ناسازگار هیچ تغییری در vault ایجاد نمی‌کند.

## ۴. هویت و امنیت دستگاه

### ۴.۱ شناسهٔ دستگاه

هر نصب یک جفت شناسه/کلید تصادفی رمزنگاری‌شده می‌سازد. شناسهٔ دستگاه از fingerprint تهاجمی، IP یا VPN ساخته نمی‌شود. IP و VPN ناپایدارند و نباید دستگاه جدید بسازند.

برای نمایش، اطلاعات محدود و قابل‌فهم ثبت می‌شود:

- نوع برنامه: Web PWA / Browser / Android / iOS؛
- مرورگر و سیستم‌عامل به‌شکل عمومی؛
- نام قابل‌ویرایش دستگاه؛
- زمان ایجاد، آخرین فعالیت، آخرین تأیید، وضعیت فعال/باطل؛
- دلیل امن revocation، بدون ذخیرهٔ دیتای فعالیت‌های شخصی.

پاک‌کردن Site Data، Incognito یا Browser Profile جدید کلید را از بین می‌برد و از دید امنیتی دستگاه جدید است.

### ۴.۲ کنترل نشست

- هر access token و refresh token به `deviceId` و نسل نشست متصل است.
- middleware تمام مسیرهای محافظت‌شده علاوه بر JWT، فعال‌بودن کاربر و دستگاه را از دیتابیس بررسی می‌کند.
- refresh روی دستگاه revoked با کد ساختاریافتهٔ `device_replaced` رد می‌شود.
- کلاینت در شروع اپ، برگشت از background، رخداد `online`، بازگشت visibility و به‌صورت دوره‌ای وضعیت نشست را بررسی می‌کند.
- اگر دستگاه باطل شده باشد، فقط credential محلی پاک/قفل می‌شود؛ vault و Export دست‌نخورده می‌مانند.
- service worker یا push می‌تواند دریافت پیام را سریع‌تر کند، ولی تضمین اجرای کد در وب‌اپ کاملاً بسته وجود ندارد. اعتبار سروری فوراً باطل است و نمایش logout در اولین اجرای ممکن رخ می‌دهد.

### ۴.۳ شمارندهٔ تعویض و قفل

یک security event فقط وقتی ساخته می‌شود که ورود موفق دستگاه جدید مجبور به حذف یک دستگاه فعال به‌علت پر بودن ظرفیت شود. شمارش بر اساس eventهای ۳۰ روز گذشته انجام می‌شود:

- تعویض‌های ۱ تا ۳: ورود موفق، revoke قدیمی‌ترین دستگاه، ثبت اعلان امنیتی؛
- تعویض ۴: عدم صدور نشست جدید، ثبت `security_locked_at` و `security_lock_reason=device_switch_limit`، revoke همهٔ دستگاه‌ها؛
- تلاش ناموفق رمز/OTP، refresh و ورود همان deviceId شمارنده را افزایش نمی‌دهد؛
- اجرای هم‌زمان دو login باید در transaction/lock سری شود تا هر دو نتوانند از سقف عبور کنند.

ادمین امکان reset رویدادهای مؤثر در شمارش یا ثبت نقطهٔ reset، unlock و تعیین `maxActiveDevices` را دارد. هر عمل ادمین در audit log ثبت می‌شود.

### ۴.۴ متن‌های کاربر

لحن متن‌ها امنیت‌محور و غیراتهامی است:

- «ورود این دستگاه به حساب شما ثبت شد.»
- «برای محافظت از حساب، نشست دستگاه قبلی بسته شد.»
- «برای محافظت از حساب، ورود موقتاً قفل شده است. لطفاً به @routino_support پیام بدهید.»

هیچ پیام عمومی از واژه‌هایی مانند «سوءاستفاده» یا «تقلب» استفاده نمی‌کند.

## ۵. اشتراک و اعتبار آفلاین

کلاینت آخرین entitlement امضاشده/تأییدشده و زمان آخرین تماس موفق را محلی نگه می‌دارد. تصمیم دسترسی:

1. اشتراک فعال و آخرین تأیید کمتر از ۱۵ روز: استفادهٔ کامل آفلاین؛
2. پایان اشتراک رسیده: گیت اشتراک طبق قوانین محصول فعال می‌شود، ولی داده و Export باقی می‌ماند؛
3. آخرین تأیید بیش از ۱۵ روز: صفحهٔ تأیید امنیت با امکان retry روی شبکهٔ ضعیف؛
4. timeout، VPN یا DNS error قبل از ۱۵ روز باعث logout یا حذف entitlement نمی‌شود؛
5. پاسخ قطعی `blocked`, `device_replaced` یا `security_locked` باعث قفل credential می‌شود، نه پاک‌شدن داده.

### اعلان پایان اشتراک

- هنگام دریافت/تغییر entitlement، دو reminder idempotent برای `expiresAt - 3 days` و `expiresAt` برنامه‌ریزی می‌شود.
- اگر زمان سه‌روزقبل گذشته ولی پایان نرسیده، اعلان missed-reminder فقط یک بار در شروع بعدی ساخته می‌شود.
- اگر اپ هنگام پایان بسته بوده و اعلان سیستمی قابل‌زمان‌بندی نبوده، اعلان پایان در اولین اجرا ساخته می‌شود.
- تمدید اشتراک reminderهای قبلی را لغو و با تاریخ جدید جایگزین می‌کند.
- زمان‌ها با timezone دستگاه نمایش داده می‌شوند، اما کلید یکتا بر اساس `expiresAt` است تا اعلان تکراری نشود.

## ۶. PWA و شبکهٔ نامطمئن

- app shell، فونت‌ها و assetهای نسخه‌شده precache می‌شوند.
- دادهٔ کاربر از IndexedDB خوانده می‌شود و API auth/payment هرگز به‌عنوان پاسخ قابل‌استفادهٔ آفلاین cache نمی‌شود.
- navigation fallback تنها routeهای خود اپ را پوشش می‌دهد؛ admin، callback پرداخت و API وارد cache نمی‌شوند.
- update service worker با پیام روشن و refresh کنترل‌شده انجام می‌شود؛ update وسط write دیتابیس نباید reload اجباری کند.
- عملیات local UI منتظر شبکه نمی‌ماند.
- درخواست‌های لازم سرور timeout، retry محدود با backoff و تشخیص offline دارند؛ عملیات حساس و غیر-idempotent مانند پرداخت بی‌دلیل retry نمی‌شوند.
- صفحهٔ تنظیمات وضعیت «فضای دائمی»، حجم مصرفی، آخرین backup، آخرین تأیید حساب، اتصال و مجوز اعلان را نشان می‌دهد.
- web notification فقط بعد از اقدام مستقیم کاربر permission می‌خواهد و برای حالت denied راهنمای رفع مجوز ارائه می‌کند.

## ۷. دیتابیس و API سرور

داده‌های مجاز سرور:

- users و credentialهای hashشده؛
- devices، session/token metadata و device security events؛
- OTP/rate-limit/login audit؛
- entitlements، grants، plans، payments و discounts؛
- admin audit؛
- feedback صریح کاربر.

داده‌های ممنوع سرور:

- categories، habits، logs، tasks، timer sessions، journal؛
- تنظیمات شخصی روزمره و محتوای backup؛
- دیتاست خام محلی یا fingerprint تهاجمی.

مسیرهای `/v1/sync/push` و `/v1/sync/pull` حذف یا با پاسخ قطعی `410 sync_disabled` بسته می‌شوند. پس از deploy کد سازگار و گرفتن backup مدیریتی در صورت نیاز، رکوردهای جدول `records` حذف می‌شوند. حذف schema/table فقط در migration جداگانه و بعد از اطمینان از نبود وابستگی انجام می‌شود.

## ۸. پنل ادمین و صفحهٔ امنیت کاربر

پنل ادمین برای هر حساب نشان می‌دهد:

- سقف دستگاه فعال؛
- دستگاه‌های فعال و revoked و آخرین فعالیت؛
- تعداد تعویض مؤثر در ۳۰ روز؛
- وضعیت و علت قفل امنیتی؛
- actionهای تغییر سقف، revoke دستگاه، revoke همه، reset شمارنده و unlock.

صفحهٔ کاربر فقط اطلاعات حساب خودش را نشان می‌دهد و امکان خروج امن از دستگاه فعلی را دارد. حذف remote دستگاه دیگر فقط در صورتی ارائه می‌شود که با سیاست سقف دستگاه ناسازگار نشود و هرگز دادهٔ محلی آن دستگاه را پاک نمی‌کند.

## ۹. قوانین و حریم خصوصی

متن فارسی و انگلیسی باید به‌روزرسانی شود:

- سرویس برای تعداد دستگاه فعال تعیین‌شده روی حساب طراحی شده و مقدار پیش‌فرض یک دستگاه است؛
- برای حفاظت از حساب، بیش از سه تعویض در ۳۰ روز قفل امنیتی ایجاد می‌کند؛
- کاربر می‌تواند برای بررسی قفل با `@routino_support` تماس بگیرد؛
- دادهٔ عادت/کار/ژورنال محلی است و پاک‌کردن دادهٔ مرورگر بدون backup قابل‌بازیابی نیست؛
- Export همیشه و Import فقط برای اشتراک پولی است؛
- اطلاعات امنیت دستگاه، حساب، اشتراک و پرداخت روی سرور نگه‌داری می‌شود.

## ۱۰. آزمون پذیرش و شرایط لانچ

### تست خودکار

- unit: vault resolution، عدم wipe، backup validation/gating، offline lease، اعلان expiry، device switch counter؛
- backend integration: login هم‌زمان، حد دستگاه، تعویض چهارم، unlock/reset، middleware device revocation، admin permissions؛
- edge parity: sync edge و اجرای کل تست Edge بعد از هر تغییر backend؛
- frontend integration: boot آفلاین، 401 قطعی در برابر timeout، account switching، migration rollback؛
- service worker: offline reload و ممنوعیت cache برای auth/payment/API.

### تست مرورگر واقعی

- Chromium desktop در عرض‌های موبایل و دسکتاپ؛
- نصب PWA، persistent storage، refresh/update و بازگشت بعد از بستن؛
- DevTools Offline، Slow 3G، latency بالا، قطع وسط درخواست و reconnect؛
- VPN-like IP change بدون ساخته‌شدن device جدید؛
- denied notification permission و recovery copy؛
- import trial/free و import paid؛
- keyboard، focus، RTL/LTR و کنتراست.

### تست مخرب و امنیتی

- replay refresh token revoked؛
- تغییر device id در body/header؛
- چهار login هم‌زمان؛
- account blocked/security locked روی تمام APIهای محافظت‌شده؛
- فایل backup بسیار بزرگ، JSON خراب، schema ناشناخته و payload حاوی credential؛
- اطمینان از نبود دادهٔ شخصی در requestهای سرور و جدول `records`.

لانچ فقط وقتی قابل توصیه است که build فرانت، تست‌های فرانت، تست‌های backend، تست Edge، parity، lint مربوط به فایل‌های تغییریافته و سناریوهای مرورگر واقعی بدون خطای حل‌نشدهٔ بحرانی یا بالا عبور کنند. عبارت «هیچ باگی وجود ندارد» قابل تضمین نیست؛ خروجی نهایی باید ریسک‌های باقی‌مانده را صریح گزارش کند.

## ۱۱. ترتیب اجرا

1. قفل‌کردن قراردادها با تست‌های failing؛
2. vault محلی و حذف wipe خودکار؛
3. دوام PWA و health/backup؛
4. schema و منطق امنیت دستگاه backend؛
5. کلاینت session/lease و UI دستگاه‌ها؛
6. import/export و اعلان اشتراک؛
7. حذف sync و پاک‌سازی records؛
8. قوانین، docs-fa، تست شبکه و مرورگر؛
9. مرور امنیتی و گزارش آمادگی لانچ.
