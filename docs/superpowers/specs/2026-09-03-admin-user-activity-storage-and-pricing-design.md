# طراحی آمار کاربر، جزئیات کشویی و مدیریت قیمت در پنل ادمین

**تاریخ:** ۱۴۰۵/۰۶/۱۲ (2026-09-03)  
**وضعیت:** تأییدشده برای پیاده‌سازی  
**خارج از محدوده:** هر نوع تغییر در کدهای تخفیف، تخفیف عمومی یا تخفیف زمان‌دار

## هدف

پنل ادمین باید با کمترین فشار پایدار روی دیتابیس، اطلاعات عملیاتی مهم هر حساب را نشان دهد و مدیریت قیمت پلن‌ها را ممکن کند. جزئیات کاربر به‌جای dialog با بازشدن کشویی زیر همان ردیف نمایش داده می‌شود و همین رفتار از فهرست پرداخت‌ها نیز در دسترس است.

## تصمیم‌های اصلی

### ۱. فعالیت کاربر بدون درخواست شبکه جدید

دو مقدار ثابت روی ردیف `users` نگه‌داری می‌شود:

- `active_days`: تعداد روزهای تقویمی یکتایی که کاربرِ واردشده حداقل یک sync موفق داشته است.
- `last_active_at`: زمان آخرین sync موفق کاربر.

ثبت فعالیت داخل همان `POST /v1/sync/exchange` موجود انجام می‌شود؛ فرانت‌اند درخواست، ping، polling یا heartbeat شبکه‌ای تازه‌ای نمی‌سازد. افزایش `active_days` با یک `UPDATE` اتمیک انجام می‌شود: اگر تاریخ آخرین فعالیت در منطقه زمانی `Asia/Tehran` با روز جاری تهران متفاوت باشد، شمارنده یک واحد زیاد می‌شود؛ در غیر این صورت فقط `last_active_at` تازه می‌شود. این منطق در برابر دو sync هم‌زمان نباید یک روز را دوبار بشمارد.

«روز فعال» به معنی حضور آنلاین ثبت‌شده است. استفاده کاملاً آفلاین فقط پس از اولین sync بعدی قابل مشاهده است و روزهای گذشته از روی حدس بازسازی نمی‌شوند.

### ۲. حجم و تعداد رکورد بدون اسکن سنگین

برای فهرست و جزئیات کاربران از دو شمارنده موجود و دقیق حساب استفاده می‌شود:

- `sync_record_count`: تعداد رکوردهای همگام‌شده فعلی حساب.
- `sync_data_bytes`: مجموع حجم JSON فعلی رکوردهای همگام‌شده.

این اعداد از ردیف `users` خوانده می‌شوند و هیچ `COUNT` یا `SUM` روی جدول بزرگ `records` در زمان بازشدن پنل اجرا نمی‌شود. عنوان UI باید «حجم داده همگام‌شده» باشد؛ این عدد حجم payload داده است، نه ادعای اندازه فیزیکی indexها و سربار داخلی PostgreSQL.

### ۳. فهرست کاربران و جستجو

پاسخ فعلی `GET /v1/admin/users` با این داده‌ها غنی می‌شود:

- شناسه، شماره، username، تاریخ ثبت‌نام
- پلن، وضعیت و انقضای اشتراک
- تعداد روز فعال و آخرین فعالیت
- تعداد رکورد و حجم داده همگام‌شده

پارامتر `q` هم شماره موبایل و هم username را جستجو می‌کند. limit فعلی حفظ می‌شود. query فهرست باید یک statement محدود باشد و برای هر کاربر query جدا اجرا نکند.

### ۴. جزئیات کشویی مشترک

در تب کاربران، کل ردیف یک کنترل قابل‌کلیک و قابل‌استفاده با کیبورد است. با بازشدن، یک ردیف جزئیات دقیقاً زیر همان کاربر قرار می‌گیرد. دکمه «جزئیات» و dialog قبلی حذف می‌شوند.

جزئیات شامل این بخش‌ها است:

- خلاصه هویت: شماره، username، شناسه حساب و تاریخ ثبت‌نام
- فعالیت و مصرف: روزهای فعال، آخرین فعالیت، تعداد رکورد و حجم داده
- وضعیت اشتراک و امکان اصلاح دستی موجود
- تاریخچه پرداخت‌ها
- دفترکل اعطای دسترسی

در هر فهرست فقط یک ردیف باز می‌ماند. اولین بازشدن از endpoint موجود جزئیات کاربر استفاده می‌کند و نتیجه تا زمان refresh تب در حافظه پنل cache می‌شود. بستن و بازکردن دوباره همان کاربر درخواست دیگری نمی‌سازد. خطا داخل همان ردیف نمایش داده می‌شود و امکان تلاش دوباره دارد.

تب پرداخت‌ها نیز ردیف‌های قابل‌کلیک دارد. کلیک روی پرداخت، جزئیات صاحب آن را با همان renderer مشترک زیر پرداخت باز می‌کند. cache جزئیات میان تب کاربران و پرداخت‌ها مشترک است. بازشدن جزئیات یک اقدام صریح ادمین است و حداکثر یک درخواست جزئیات برای هر کاربر در هر بار بارگذاری پنل ایجاد می‌کند.

### ۵. مدیریت قیمت پلن‌ها

یک تب «پلن‌ها» اضافه می‌شود. اطلاعات از endpoint ادمین خوانده می‌شود و برای هر پلن نام، مدت، وضعیت و قیمت فعلی را نشان می‌دهد. در این مرحله فقط `price_toman` قابل ویرایش است؛ شناسه، مدت، نام و فعال/غیرفعال‌بودن دست نمی‌خورند.

تغییر قیمت:

- فقط عدد صحیح مثبت و در بازه امن پذیرفته می‌شود.
- قبل از ذخیره، پنل قیمت قدیم و جدید را در تأیید نهایی نشان می‌دهد.
- mutation با نشست ادمین و CSRF موجود محافظت می‌شود.
- قیمت مستقیماً در جدول server-authoritative `plans` ذخیره می‌شود؛ کلاینت هیچ مبلغی به checkout تحمیل نمی‌کند و تاریخچه پرداخت‌های قبلی تغییر نمی‌کند.
- cache عمومی `/v1/plans` در Cloudflare ممکن است قیمت نمایشی را حداکثر ۵ دقیقه دیرتر نشان دهد. پنل این تأخیر را صریحاً کنار عملیات ذخیره نمایش می‌دهد. مبلغ نهایی checkout همچنان از دیتابیس سرور محاسبه و در payment ذخیره می‌شود.

### ۶. زبان بصری و دسترس‌پذیری

پنل در حالت «Operate» طراحی می‌شود: سریع برای اسکن، متراکم ولی آرام، و هماهنگ با هویت نارنجی/کرم خود اپ.

- فونت Vazirmatn واقعاً بارگذاری می‌شود و fallback امن دارد.
- hierarchy تیتر، فیلتر، کارت، جدول و جزئیات روشن می‌شود.
- ردیف بازشونده حالت hover، focus-visible و `aria-expanded` دارد.
- در موبایل، اطلاعات اصلی بدون اسکرول افقی اجباری به کارت‌های stacked تبدیل می‌شوند؛ جدول‌های تاریخچه داخل جزئیات می‌توانند اسکرول کنترل‌شده داشته باشند.
- loading، empty و error state داخل همان بخش باقی می‌مانند و کل پنل را نمی‌پراند.
- انیمیشن بازشدن کوتاه و محترم است و `prefers-reduced-motion` را رعایت می‌کند.

## قراردادهای بک‌اند و Edge

- منطق مشترک در `backend/src/` پیاده می‌شود.
- schema و serviceهای مشترک با `npm run sync:edge` به `supabase/functions/api/shared/` تولید می‌شوند.
- route ادمین و route sync در Edge چون hand-maintained هستند، همراه Fastify تغییر داده و با تست parity/Edge بررسی می‌شوند.
- ستون‌های تازه فعالیت مثل شمارنده‌های quota در projection عمومی Drizzle قرار نمی‌گیرند تا deploy کد جدید پیش از migration، queryهای عمومی `users` را روی schema قدیمی نشکند.
- migration فقط additive است: دو ستون فعالیت با default امن و constraint غیرمنفی.

## خطا و ایمنی

- شکست ثبت activity نباید نتیجه sync و حفاظت از داده کاربر را پنهانی موفق جلوه دهد؛ عملیات در مسیر سرور تست می‌شود و خطا قابل مشاهده باقی می‌ماند.
- مقدارهای شمارنده هنگام خواندن به عدد امن تبدیل می‌شوند و مقدار منفی یا نامعتبر در UI نمایش داده نمی‌شود.
- خطای تغییر قیمت پاسخ 4xx روشن دارد و قیمت قبلی را حفظ می‌کند.
- هیچ secret، داده داخل journal/task/habit یا محتوای رکوردهای شخصی وارد فهرست ادمین نمی‌شود؛ فقط metadata و تاریخچه‌های عملیاتی موجود نمایش داده می‌شوند.
- قابلیت block، device tracking، revoke یا کنترل cloud-only جدید اضافه نمی‌شود.

## تست و معیار پذیرش

### بک‌اند

- اولین sync روز، `active_days` را یک واحد زیاد و `last_active_at` را ثبت می‌کند.
- sync دوم در همان روز تهران شمارنده را زیاد نمی‌کند ولی آخرین زمان را تازه می‌کند.
- عبور از نیمه‌شب تهران روز تازه را دقیقاً یک‌بار می‌شمارد، حتی با درخواست هم‌زمان.
- فهرست کاربران username، فعالیت، تعداد رکورد و حجم را در یک query محدود برمی‌گرداند.
- جستجوی شماره و username هر دو کار می‌کنند.
- جزئیات کاربر همان metadata را همراه پرداخت و grant برمی‌گرداند.
- فهرست پلن و تغییر قیمت با auth، CSRF و validation پوشش دارد؛ checkout بعدی قیمت جدید را server-side استفاده می‌کند.
- routeهای Fastify و Edge قرارداد یکسان دارند.

### پنل

- دکمه و dialog جزئیات وجود ندارند؛ کلیک و Enter/Space روی ردیف accordion را باز می‌کند.
- فقط یک ردیف در هر فهرست باز است و `aria-expanded` درست تغییر می‌کند.
- بازشدن دوباره کاربر cache‌شده fetch تازه ایجاد نمی‌کند.
- کلیک روی ردیف پرداخت جزئیات صاحب حساب را نمایش می‌دهد.
- جستجو copy مناسب شماره/username دارد.
- تغییر قیمت به تأیید نیاز دارد و پس از موفقیت مقدار نمایش‌داده‌شده تازه می‌شود.
- نمای desktop و mobile، فونت و reduced-motion به‌صورت بصری بررسی می‌شوند.

### مجموعه بررسی نهایی

- تست‌های هدفمند admin، sync، pricing و Edge
- `npm run sync:edge` و تست parity
- lint و typecheck مرتبط
- build وب و backend
- بررسی تصویری یک‌مرحله‌ای در desktop و mobile و یک مرحله تأیید پس از اصلاح

## مرز انتشار

این کار فقط کد، migration و تست محلی را آماده می‌کند. اجرای migration، deploy Edge/Worker/Pages و تغییر قیمت واقعی production نیازمند تأیید جداگانه کاربر است.
